В MVP предлагается выделить отдельную платформу публикации ставок внутри банка. Она становится единым контролируемым контуром между источником ставок и потребителями: внутренним кол-центром и партнерским кол-центром. Источник ставок остается в банковском контуре, а публикация на потребителей автоматизируется.

Для внутреннего кол-центра наиболее удобен API-подход: оператор должен видеть актуальные ставки в своей системе без ручного переноса файлов. Для партнерского кол-центра API недоступен по условию задачи, поэтому остается файловая интеграция через SFTP. Это делает архитектуру двуканальной: API для внутренних потребителей и SFTP для внешнего партнера.

Контейнерная модель внутри банка включает хранилище ставок, API публикации, генератор файлов, SFTP-публикатор, аудит и мониторинг. Такой подход убирает Excel и переписку из критического пути, а также позволяет отследить версию каждой опубликованной ставки.

На годовом горизонте целевое состояние должно уйти от ручного распределения и от файлов как основного способа подготовки данных: ставки ведутся в едином банковском контуре, внутренний кол-центр получает их по API, а партнерский контур продолжает получать автоматически сформированные SFTP-файлы. Это сохраняет совместимость с ограничениями партнера и одновременно снижает операционные затраты банка.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

Опишите здесь наиболее важные альтернативные решения.

1. Оставить Excel и ручной обмен ставками. Это дешевле на старте, но не решает проблему перегрузки и не дает управляемого источника правды.
2. Сделать API и для партнера. Это технологически лучше, но противоречит ограничению задачи и не подходит для внешней системы партнера.
3. Вынести публикацию ставок только в АБС. Это усиливает зависимость от перегруженной АБС и не позволяет удобно обслуживать внешний канал.
4. Построить событийную шину с очередями вместо SFTP. Это перспективно, но для текущего банка и партнерского канала избыточно и не отвечает условию по внешней системе.

**Недостатки, ограничения, риски**

Подробно опишите здесь недостатки, ограничения и риски выбранного решения.

1. Партнерский канал остается файловым, поэтому он не получает преимущества онлайн-API и будет иметь задержку по расписанию выгрузки.
2. Если источник ставок продолжит жить в ручном процессе, то банковский контур публикации будет зависеть от дисциплины бэк-офиса.
3. Любая ошибка в формате файла может затронуть внешний кол-центр, поэтому требуется строгая валидация и контроль версий.
4. Поддержка двух каналов распространения ставок повышает сложность мониторинга и эксплуатации.
5. При дальнейшем росте нагрузки может понадобиться переход к более событийной архитектуре и дополнительному слою интеграции.
